# Fault Taxonomy — the guardrails, and why they exist

**Status:** active
**Category:** C
**Created:** 2026-11-19
**Last updated:** 2026-11-19
**Owner:** primary agent — owner-accepted decision, 2026-11-19

> **Decision, 2026-11-19 (owner, accepting the primary agent's recommendation).**
> The reasoning below is not context. It is the **rule**, and `scripts/validate-fault-taxonomy.cjs`
> fails the build when a rule is broken. A standard in a paragraph costs tokens every turn; a
> standard in a failing command costs nothing.

---

## What was proposed, and what was accepted

A system that records **persistent faults**, makes them **regularly visitable**, diagrams the
**pathways** they sit on, and **links each to a GitHub issue** — one screen, context plus evidence.

**Accepted:** a named fault with an instance, a recurrence count, an owner, and a generated view.
**Rejected:** hand-drawn "every eventuality" diagrams and a taxonomy nothing visits.

---

## The four rules

### 1 · A fault is an INSTANCE WITH AN OWNER, never a phrase

It must be countable (`count`), ageable (`firstSeen`/`lastSeen`), evidenced (`evidence`) and owned
(`issueUrl`). A table of *(title, detail)* records the same fault twice under two spellings and can
never answer "how often".

**Measured here:** `decision_log.reason` is free text, so nothing can count a decision reason.
57 `TCS-*` notice codes are UI copy with no history. `ProviderDegradationService` keeps its state in
`new Map()` — **lost on restart**, and no `provider_degradation` table exists.

> 🛑 **G1** — a `Fault` model missing `code, firstSeen, lastSeen, count, evidence, issueUrl, status`
> fails the build.

### 2 · RETIRE, never DELETE — and an issue close is a trigger, not a deletion

The whole value is **recurrence**: a code deleted when its issue closes destroys the evidence that it
ever happened, so the next occurrence looks brand new.

> **The project's instinct was right about the trigger and wrong about the verb.** Closing an issue MAY
> retire a fault code; it may not remove it. Retirement is a `status` change and the row stays, so
> "this came back" remains answerable.

> 🛑 **G2** — any `fault.delete`, `fault.deleteMany` or `DELETE FROM fault` in source fails the build.

### 3 · A diagram is GENERATED, or it is documentation — and documentation decays

`docs/PIPELINE-MAP.md` is the precedent that survives here: regenerated by a script, and `--check`
fails the build when it is stale. A hand-drawn pathway with every eventuality marked on it is
accurate once, and wrong the first time a branch is added.

> 🛑 **G3** — a `docs/` file whose name names faults and which contains a diagram must carry a
> `GENERATED` marker near the top.

### 4 · A registry with no cadence is a graveyard

Not machine-checkable, and therefore stated as the load-bearing constraint rather than a rule:
**code cannot make anyone visit.** `REVIEW-QUEUE.md` exists because lists rot when nobody is
prompted. Any registry built on these rules must surface **"not visited in N days"** on a page that
is already opened — not create a new page nobody opens.

---

## Build order (deliberately inverted from the proposal)

| Step | Why first |
|---|---|
| 1 · `fault` table + `faults.record(code, evidence)` writers | without an instance there is nothing to count, age or link |
| 2 · registry screen with a **staleness counter** | the cadence is the point; the view is how it is kept |
| 3 · **generated** mermaid from the registry | cheap once 1 exists, and cannot decay |

⚠️ **Do not build step 3 first.** A diagram is the most impressive artefact and the least useful
without a registry behind it — and it is the one that rots.

## How to change this decision

Deliberately, with a register row that says what changed. Do **not** widen a rule to make a build
green: a guard that fires for the wrong reason gets allowlisted, and an allowlisted guard is worse
than none. Register rows: `docs/SETTLED-DECISIONS.md` 226 and 227.
