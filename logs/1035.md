## What is wrong

`POST /reconnect` can connect a bridge to a **different MT5 account than the one it was configured
for**, and report **`success: true`**. The bridge's stated identity and its actual session then
disagree, with nothing reporting it.

Found 2026-09-30 while running #1000's `:5002` canary.

## Evidence — measured, verbatim from the bridge log

Canary started with `BRIDGE_PORT=5002`, `MT5_ACTIVE_ACCOUNT=9`, `MT5_ACCOUNT_9=99999999`,
`MT5_SERVER_9=NoSuchServer-Demo`:

```
16:04:15,162 [INFO]  [broker9] Initializing MT5: server=NoSuchServer-Demo, account=99999999 (account #9)
16:04:20,730 [ERROR] [broker9] MT5 initialization failed: (-10005, 'IPC timeout')
16:04:45,108 [ERROR] [broker9] MT5 connection state -> terminal-down … Remedy: POST …/reconnect

── then the POST ──
16:04:56,501 [WARNING] [broker9] Reconnecting MT5: explicit POST /reconnect
16:04:57,502 [INFO]    [broker9] Initializing MT5: server=NoSuchServer-Demo, account=99999999 (account #9)
16:04:59,775 [INFO]    [broker9] MT5 connected: 62135531 @ PepperstoneUK-Demo, balance=1065.04
16:04:59,776 [WARNING] [broker9] MT5 reconnect SUCCEEDED — account=62135531 balance=1065.04
```

The HTTP response was:

```json
{"success": true, "state": "ok", "account": "62135531", "balance": 1065.04}
```

**The bridge asked for `99999999 @ NoSuchServer-Demo` and attached to `62135531 @
PepperstoneUK-Demo`** — the real account held by the running MT5 terminal. `mt5.initialize()` with a
login/server that cannot be honoured appears to **fall back to attaching to the terminal that is
already running**, rather than failing.

So every field the bridge reports about itself is now wrong: `account`, `server`, `activeAccount`,
and `/health` says `connected: true`.

## Why this matters — a bridge is an ACCOUNT SCOPED THING

A bridge is addressed per broker (`MT5_ACTIVE_BROKERS=2,3` → `:5000` account A, `:5001` account B).
Everything downstream assumes that binding:

| Consumer | Assumes |
|---|---|
| `Mt5ConnectionManager.getUrl(brokerId)` | `:5001` is broker 3's account |
| the stop guardian / time-stop | a ticket on `:5001` belongs to that account |
| risk caps, position sizing | the account's balance and equity |
| `trade.brokerTicket` reconciliation | the ticket is the one this bridge reported |

⚠️ **And the automatic recovery watchdog makes this reachable without a human.** `#992` option B
(`Mt5SessionRecoveryService`) POSTs `/reconnect` on its own when a bridge answers with a dead
session. If the terminal is logged into a different account at that moment, the watchdog **silently
binds the bridge to that account and records success** — turning a recoverable outage into a
wrong-account session.

## ⚠️ It is the same defect class this repo has been fixing, one level down

**The bridge's `account` is a NAME, and a name is a claim.** Nothing verifies it against the writer.
`connect_mt5()` asks; `mt5.initialize()` decides; and no code compares the answer to the request.
That is `reachable` all over again — a status surface that merges "as configured" with "as it
actually is".

## Acceptance

- [ ] After every connect/reconnect, the **requested** account and server are compared with the
      **actual** `terminal_info()` / `account_info()` login and server, and a mismatch is reported
      **as an error naming both** — never as `success: true`
- [ ] `POST /reconnect` returns a distinct, non-success outcome for a mismatch (a caller must not read
      it as the bridge being healthy)
- [ ] The mismatch is visible on `/health` (`connectionState`), so the API's `answered`/`reachable`
      pair can carry it
- [ ] Reproduced as a canary: point a bridge at an unreachable server while a terminal is logged into
      a different account, and assert the mismatch is reported
- [ ] Decide and record: on a mismatch, does the bridge **refuse to serve orders**? (A bridge on the
      wrong account is arguably worse than a bridge that is down — the down one refuses, the wrong one
      accepts.)
