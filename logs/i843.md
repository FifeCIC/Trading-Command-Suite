# Position sizing: the backtester can size a trade four ways, the live path can size it one way

## Summary

`backtest.service.ts` implements **four** position-sizing models, including ATR equal-risk (#271) and
Kelly (#269). The **live trading path has no sizing model at all** — it reads a fixed lot from the
strategy record.

```ts
// automation-loop.service.ts:1545
const baseSize = strategy.baseSize ?? 0.01;
```

That value travels unchanged into the broker call:

```
baseSize → broker.placeOrder({ quantity: baseSize })   // automation-loop.service.ts:389 and :1724
```

| What | Where | Detail |

| Live quantity | `automation-loop.service.ts:1545` | `strategy.baseSize ?? 0.01` — fixed lot, default 0.01 |

| Read-back only | `automation.controller.ts:272`, `decision-chain.service.ts:255` | `tradeVolume` surfaced for display — not used to size anything |

## Why this matters (the theory)

**Two different lot sizes make a backtest unable to describe the system it is testing.**

A backtest that sizes with `atrEqualRisk` is answering *"what would this edge have returned if every
trade risked 1% of equity?"*. The live loop answers *"what does this edge return at 0.01 lots on every
symbol and every market?"* Those are different experiments. The backtest's return, drawdown and
Sharpe numbers therefore **do not transfer**, and — importantly — they fail in the direction that
looks fine: 0.01 lots on EURUSD and on XAUUSD are not remotely the same risk (gold's ATR is an order
of magnitude larger), so a live P&L will not resemble the backtest even if the entry logic is
perfect. This is the same defect class the repo already documents elsewhere: **plausible numbers with
no error message.**

Fixed lots also mean the system's *risk per trade* is an accident of the symbol rather than a
parameter. Equal-risk sizing is the standard mechanism that makes a composite score's conviction
comparable across instruments.

## Proposed scope

Smallest correct version — introduce **one** sizing function and give the live path the same models
the backtester already proves:

1. **Extract the sizing decision into a single shared function** (one implementation, called by both
   the backtester and the live loop). Two copies will drift; `shared-core.instructions.md` is explicit
   that a second implementation is the most expensive kind of debt.
2. **Add `atrEqualRisk` to the live path first** — it is the highest value and the maths already
   exists. It needs: ATR for the symbol (available), stop distance (already computed as `sl`),
   account equity, and a `riskPct` config.
3. **Keep `fixedDollar` / `fixedPercent` / Kelly as options** the strategy can select, so behaviour is
   chosen rather than implicit. Default for existing bots must remain fixed-lot until deliberately
   migrated.
4. **Round to the broker's volume step.** `volumeMin` / `volumeMax` / `volumeStep` already travel with
   the symbol from the bridge (`mt5_bridge_v2.py:725-737`) — sizing must clamp and round to those, or
   a correct calculation becomes a rejected order (`TCS-TRADE-011`/`-012` already exist for min/max).

## Acceptance criteria

- [ ] One sizing implementation; the backtester and `automation-loop` call it. No second copy.
- [ ] With `atrEqualRisk` selected, two symbols of very different volatility risk the same fraction of
      equity on the same `riskPct` — demonstrated on a demo account, not asserted.
- [ ] The resulting volume is rounded to the broker's `volumeStep` and clamped between `volumeMin` and
      `volumeMax`; an unclampable calculation fails **visibly**, with a notice code, not silently.
- [ ] A backtest run with the model used live reproduces live sizing for the same inputs.
- [ ] Existing fixed-lot bots are unchanged until their config is deliberately migrated.
- [ ] Testing proves the model, not just that a trade happened. **A test that passes for the wrong
      reason is worse than no test** (see the bar-ordering handoff for a worked example of this trap).

## Guardrails that must NOT be bypassed

This is a **money-moving path** — per `development-status.instructions.md` it keeps full care: risk
limits, order guards, duplicate guard, stop guardian, margin checks. Sizing must be computed
**before** `assessGlobalRiskLimits()` (currently called with `baseSize` at
`automation-loop.service.ts:342`), so the risk gate sees the real exposure rather than a placeholder.

## Out of scope

- Kelly's win-rate prior is a hard-coded 0.5 (`backtest.service.ts`, "neutral prior"). Improving it
  requires trustworthy measured accuracy, which is a separate issue.
- Any AI/LLM input to sizing. See `docs/theories/DETERMINISTIC-CORE-AI-FRAMING.md` — sizing is a
  deterministic decision and stays one.
- Live portfolio-level correlation sizing (the `position-time-stop.service.ts:26` note already flags
  correlated FX/gold exposure as a *volume* problem and warns that raising a cap converts a size
  problem into a correlation problem).
