## Summary

`SpeedScanService` is a **second scoring path** that the automation loop knows nothing about, and its hardcoded fallback map **declares inactive protocols active**. An `active = 0` protocol is therefore still being scored and **persisted** to the shared `score` table every ~20–40 seconds.

Found while completing Step 3 of #772.

## Evidence (2026-09-11)

`usdcad-oil-v1` — `active = 0`, **no bot**, **no symbol assignment**, **absent from `protocol_score_status`** (the loop never scores it) — is writing `score` rows continuously:

```
strategyId='usdcad-oil-v1'  value=85  22:30:22.165Z
strategyId='usdcad-oil-v1'  value=85  22:27:23.051Z
strategyId='usdcad-oil-v1'  value=85  22:26:57.233Z
strategyId='usdcad-oil-v1'  value=85  22:26:37.664Z
… continuing every ~20–40s
```

42 score rows, most recent within seconds of the query.

## Root cause

Three lines combine:

**1.** `protocol-gating.service.ts:1400` persists with `strategyId = protocolId`, so *any* caller of `scoreWithGating()` writes under that protocol's name into the shared `score` table.

**2.** `speed-scan.service.ts:122` hardcodes a symbol→protocol map:

```ts
USDCAD: 'usdcad-oil-v1',
```

**3.** `resolveProtocolForSymbol()` (speed-scan.service.ts:155) tries the DB first via `symbolProtocolAssignment` — **which is empty** — so every symbol falls through to:

```ts
// Fall back to hardcoded map — all hardcoded protocols are active by default
if (SYMBOL_PROTOCOL_MAP[symbol]) return { slug: SYMBOL_PROTOCOL_MAP[symbol], active: true };
```

**That `active: true` is hardcoded, not read.** The real `Protocol.active` flag is ignored on this path.

`DEFAULT_SPEED_SYMBOLS` includes `USDCAD`, so the scan scores it and the gating service persists the result.

## Consequence

**`active = 0` is not a kill switch for this path.** A protocol marked inactive can still:

- write rows to the shared `score` table,
- appear in score history and any trend/peak analysis built on it,
- influence `observeAdaptiveTargetPeak()` (called in the same persist block), i.e. an inactive protocol's observed peak can be raised by these writes.

This is the **"plausible numbers with no error"** class the repo has hit repeatedly (`meta-stack-contracts.instructions.md`). Nothing errors; an inactive protocol simply contributes data.

## Wider risk — possible phantom protocol slugs

`SYMBOL_PROTOCOL_MAP` also maps to protocols that may not exist in the `protocol` table at all:

`dow-speed-v1`, `nikkei-speed-v1`, `euro-stoxx-v1`, `oil-speed-v1`, `btc-scalp-v1`, `leverage-v2`

Because `score.strategyId = protocolId`, those would land in the **shared** `score` table under slugs no `Protocol` row owns. Needs measuring — I have not done so.

## Scope of the fix

1. **Measure** — list every `score.strategyId` with no matching `protocol` row (phantom slugs), and count rows per phantom.
2. **Decide the rule** — should `DEFAULT_SPEED_SYMBOLS` / `SYMBOL_PROTOCOL_MAP` be able to score at all now that scoring is protocol-driven? The map predates the 2026-08-11 protocol-driven refactor and the 2026-09-02 retirement of strategy-side scoring (#714).
3. **Make `active` authoritative** — either drop the hardcoded fallback, or have the fallback read real `active` from the DB and skip inactive protocols.
4. **Stop persisting from non-canonical paths** — `scoreWithGating()` currently persists for *any* caller; consider whether analytics/screening callers should be able to write to `score` at all.
5. **Guard** — a validator that fails if a `score.strategyId` does not resolve to an **active** `protocol` row.
